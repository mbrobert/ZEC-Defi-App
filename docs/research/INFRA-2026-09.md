### C.2 The return leg (yield → native ZEC → shielded address)

This is the leg the audit flagged as mattering as much as entry. What each route can actually do today:

| Route | Pays ZEC to `u1…` / shielded? | Practical pattern to reach a shielded balance | Leak surface |
|---|---|---|---|
| NEAR Intents (public or confidential) | No (t-address only) | Pay to a **fresh, single-use t-address** controlled by the user's wallet; wallet auto-shields (Zashi/Cake pattern). ECC's promised "ephemeral addresses + shielded refunds" would formalise this on the wallet side. | Amount and timing of the t-address receipt are public; if the same t-address is reused across payouts, payouts are linkable (the ZachXBT refund issue in reverse). |
| Maya | **Yes** | Put the `u1…` address in the swap memo as destination; Maya's validators sign a shielded output verified via an OVK derived from the vault key. | Inbound side still needs a memo from a transparent (or shielded+memo, once issue #219 ships) send. |
| THORChain | No | As NEAR Intents. | As NEAR Intents; additionally new/thin pool. |
| cbZEC | Via Coinbase withdrawal | KYC'd account withdrawal; address type unverified. | Full KYC linkage. |

Protocol-level note: a z→t **deshielding** send to any service's t-address deposit works with every route (it is an ordinary Zcash transaction), so "shielded accepted?" is really a question of (a) whether the service *needs a memo* (Maya: yes; NEAR/THORChain: no, the deposit address is quote-specific), and (b) what is leaked. Source for the memo constraint: [hhanh00 Maya docs](https://hhanh00.github.io/docs/maya_protocol/index.html).

## D. Infrastructure that could remove risk or complexity

### D.1 The identity problem — passkey / account-abstraction options

**Structural observation (not a recommendation).** Every passkey option converts the question from "who holds the key" into "what scope does the operator's delegated key have". The two mechanisms with the narrowest, user-revocable scope that work with no wallet install on Base are Base Account Spend Permissions and ZeroDev session keys. Neither removes the operator entirely; both remove *unbounded* custody. A user who closes the browser recovers the position via their passkey (synced by the platform authenticator), not via payout address. Passkey loss without a platform sync = position loss unless a recovery signer is added — a new failure mode to weigh against the current one.

## What this enables (options, not recommendations)

**Shielded-ZEC bridging.**
- *Maya as the return leg.* Maya is the only permissionless venue that pays ZEC to a `u1…` address today (SwapKit-confirmed), with a ~$4.4M ZEC pool. That makes a split design possible: NEAR Intents (or THORChain) for ZEC→USDC entry, Maya for USDC/ETH→shielded-ZEC exit. SwapKit already encodes the constraint (`zcashUnifiedAddressUnsupported`), so a single aggregator call can enforce "shielded exit ⇒ Maya".
- *Rotating t-address + wallet auto-shield* as the fallback return path on NEAR/THORChain, which is what Zashi and Cake do; the leak surface is amount/timing at the t-address, not a persistent identifier if each payout uses a fresh address.
- *Confidential Intents* hide the middle of the route but not the ZEC edges; it changes what a chain observer can see about the USDC side, not the ZEC side.
- *Second and third venues now exist* (THORChain ZEC since 25 Aug 2026; cbZEC since ~1 Sep 2026), so a venue-failure playbook can have real alternates — with the caveats that THORChain is post-exploit and thin, and cbZEC is custodial/KYC.
- *Pool migration matters:* Orchard is exit-only; "shielded" now means Ironwood/unified. Any hard-coded Orchard assumption (e.g. Zwap) is stale.

**No-login user ownership.**
- A Base Account (passkey-owned 4337 account, in-browser, RIP-7212 at ~3.5k gas) can hold the position NFT/vault shares. The operator becomes a **Spend Permission spender** (bounded token/period allowance, user-revocable) or a **ZeroDev session key** rather than a custodian. Recovery is by passkey, not payout address. Paymaster sponsorship removes the "user needs ETH" problem.
- Alternative: keep payout-address identity but move the operator key into **OpenZeppelin Relayer + KMS/Turnkey** with per-network policies, which addresses key-handling risk without changing the ownership model.
- Trade-off to weigh: passkey loss without platform sync vs. today's operator-custody hop.

**Managed-CL alternative to Snuggle.**
- Steer is the only manager with a published fee, and it is the same 15%. Gamma is cheaper on paper (~10%, 2023 source) but has $57k on Base and three hacks. Arrakis has the most Base TVL ($14.4M) but an unverified fee and a protocol-level revenue/fees ratio near 50%. Aerodrome's own ALM (Mellow) is the only option that is *guaranteed* to keep gauge emissions, with a fee that could not be verified from public pages.
- Enso's route API can express "USDC → CL vault share" as one atomic transaction, which would shrink the custom position-management code regardless of which manager is chosen.

**Execution.**
- CoW on Base gives batch-auction MEV protection with a 2 bps volume fee and free expiry of unfilled orders; 0x is $1,000/mo + 0.15%; Socket is free with optional integrator bps. All are USDC-side only.

**Data.**
- Pyth has a live `Crypto.ZEC/USD` feed (id above), usable on Base for payout-side pricing and health checks; Chainlink lists a ZEC/USD CEX-price stream. DefiLlama's official MCP exposes `get_yield_pools` for rate monitoring under a paid subscription.

**Security.**
- Slither + Aderyn in CI, Halmos over existing Foundry tests, Tenderly simulation before every operator tx, and OpenZeppelin Relayer (v1.5.0) for the operator key — all free except Tenderly Console.
