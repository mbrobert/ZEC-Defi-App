# Internal audit — what widening the invariant fuzz found (2026-09-16)

Not an audit wave. This is the record of a **coverage** pass — `docs/BACKLOG.md` §6, the eight
reaches `AUDIT-2026-09-11.md` W3-MED-3 named and left open — and of the two things that fell out of
it once the fuzzer could get to states it had never been able to build.

Abbreviations on first use: LP = liquidity provision; NPM = the Aerodrome/Slipstream non-fungible
position manager; HF = health factor; LTV = loan-to-value.

**Tree:** the working tree at `3eb6937` on `main`. **Suites:** contracts 433 → **435 passed / 0
failed / 13 skipped** (448 total, 39 suites); the invariant group re-run deep at **1,500 runs ×
120 depth = 180,000 calls, 2,150 reverts, 0 failures**.

**Neither finding is a safety defect** under `docs/ROADMAP.md` rule 3 — neither can lose or lock a
user's funds, and neither lets the keeper exceed its grant. Both are recorded, both are pinned by a
test so they cannot change silently, and both go to the auditors as questions rather than as fixes.

## What the pass did

Nine actions were added to `contracts/test/invariant/Handler.sol`, covering W3-MED-3's eight lettered
gaps, and every one of them is proved to reach its branch by
`test_theEightNamedGapsAreReached` — on the branch's effect, not on the call returning, because an
action that is registered but no-ops widens nothing and the difference is invisible from a run count.

| Gap | Action | What proves it was reached |
|---|---|---|
| (a) dead gauge | `deadGauge` | `claimStakingRewards` reverts `NoRewardAdapter()` on an un-gauged entry, so `_claimOne`'s **harvest fallback** runs and the owner is still paid. That `try/catch` had never been taken under fuzz |
| (a) residual | `singleSidedResidual` | the enumeration window's own-position residual is armed |
| (b) increase ×2 | `increaseLp`, `increaseDirectLp` | the id set grows by one on each venue — the only call that grows it without `open` |
| (c) fixed withdraw | `ownerWithdrawAmount` | `CollateralShort` refuses and **nothing moves**; a dust withdraw still succeeds. Every withdraw before this was `max`, so the two gates standing between a user and an accidental liquidation were unreachable |
| (d) WETH switch | `switchVenueWeth` | WETH's own registry pointer moves and returns; `previousVenues` is per-asset, so cbBTC's coverage said nothing about WETH's |
| (e) single revoke | `revokeOne` | `grantOf(...).active` goes false and the keeper is refused after it — a different code path from `revokeAll`'s epoch bump |
| (f) pool misbehaving | `poolMisbehaves` | the pool settles the callback short and fills half, and the adapter still ends holding nothing of either leg |
| (g) engine paused | `pauseEngine` | the owner's raw `exec` exit succeeds with the engine **stopped** — invariant 1, finally run in the state it was written for |
| (h) unstaked, then refused | `closeManyDirectRefused` | the id leaves the gauge and the NPM refuses, so it ends in `failed` and out of the gauge |

(h) needed one new hook on a test double: `MockSlipstreamNpm.setRefuseDecrease`. The gauge's existing
`refuse` blocks *unstaking*, which reaches a different and already-reachable state — the id never
leaves the gauge. Only a refusal on the manager's side produces the branch the audit named.

## W4-OBS-1 · The one-click Close has no tolerance for a single stuck position

**Severity.** Observation (availability). Not safety: nothing is lost or locked, and the owner's raw
`exec` exit is asserted to still work in the same state.

**Where.** `contracts/src/router/StrategyRouter.sol`, `unwind`.

**How it was found.** The 1,500-run sweep broke `invariant_singleCloseClearsEveryBook` on an
eight-call sequence, once `closeManyDirectRefused` could leave a position manager refusing across
calls.

**The failing scenario**, replayed deterministically in
`test_obs_singleCloseUnderARefusingPositionManager`:

1. the registry points cbBTC at Morpho; the owner opens there;
2. an engine LP position is opened;
3. the registry points back at Aave and the owner opens there too — **two books**;
4. a direct-venue LP position is opened;
5. the position manager refuses `decreaseLiquidity`;
6. the owner's one-click Close — `unwind(ids, repay max, withdraw max)`, funded with more than
   enough USDC to clear every book — **reverts entirely.**

The debt it would have repaid is untouched and the USDC never leaves the account, although the stuck
position has nothing to do with either book.

**Why it is worth a question rather than a shrug.** `closeMany` returns a `failed` array precisely so
one stuck id does not sink the rest; `unwind` does not inherit that tolerance. And the refusal is not
only a mock switch: a real `decreaseLiquidity` reverts on its own slippage check against a moved
price, or on a deadline — so the shape is reachable without anybody behaving badly.

**What is NOT true**, and was checked rather than assumed: on a ONE-book account the same refusal
does not stop the Close. A first attempt to reproduce it that way passed, which is why the scenario
above is the two-book one.

**Not fixed here.** Giving `unwind` partial-failure tolerance is a change to money movement across a
trust boundary and a product decision about what a half-finished Close should leave behind. It goes
to the founder and to the audit firms as a question. **Pinned by:**
`contracts/test/invariant/Invariants.t.sol`,
`test_obs_singleCloseUnderARefusingPositionManager` — which asserts today's behaviour, so a
deliberate change turns it red rather than passing unnoticed.

## W4-OBS-2 (backlog G-1) · `tokenBudgetOf` keeps reporting a revoked grant's budget

**Severity.** Observation (reporting). Not safety: the authorisation path reads the expiry that
`revoke` zeroes, and the keeper is refused — asserted in the same test.

**Where.** `contracts/src/account/OilskinAccount.sol`, `tokenBudgetOf`.

**What it is.** `revoke` kills a grant by setting `g.expiry = 0`. `grantOf` computes and returns
`active` from that. `tokenBudgetOf` is the one grant view that does **not** consult expiry: it
returns the raw `g.tokenLimit[token]`, so after a revoke it still reports the full budget —
100,000 USDC in the fixture.

**How it was found.** Gap (e) above, on its first run: an assertion written against `tokenBudgetOf`
failed where the same assertion against `grantOf(...).active` passes.

**Why it is not user-visible today.** `web/lib/reads.ts` `readKeeperGrant` reads `grantOf` first and
carries its `active` through, and `web/components/KeeperPanel.tsx` gates the budget rows on it. An
**integrator** reading `tokenBudgetOf` on its own would over-report a revoked keeper's remaining
budget — which errs towards alarming the reader, not towards trusting a keeper that cannot act.

**Not fixed here.** It is a one-line change to an audited contract, for a reporting gap with no
user-visible effect, on a tree heading for a freeze. **Pinned by:**
`contracts/test/invariant/Invariants.t.sol`, inside `test_theEightNamedGapsAreReached` — today's
behaviour asserted by name, referencing backlog G-1, so it cannot change without someone reading the
entry.

## One thing the pass deliberately did not do

`closeManyDirectRefused` disarms the refusal in the same call. Left armed it makes
`invariant_singleCloseClearsEveryBook` fail — which is W4-OBS-1, and is recorded above rather than
asserted by leaving the world permanently broken. The action's job is to reach the branch; a probe
that runs afterwards is entitled to an operable world. Weakening the invariant to accommodate the
armed state was the other option and would have quietly cost the suite a property it has today.
