# Internal audit — the cross-chain keeper path, read adversarially the day it gained its adapter (2026-09-25)

**Scope.** The first part of ROADMAP H3's "internal audit wave over everything merged since 2026-09-16":
the Solana keeper's bridge route and what it hands the Base keeper — `agent/src/solana/dispatcher.ts`,
`monitor.ts`, the new `baseBurner.ts` and `circleFees.ts` (`d0e4262`), `agent/src/dispatch/keeperDispatcher.ts`
`dispatchBurn` / `confirmBurn`, `dispatch/policy.ts` `planBurn`, and `packages/shared` `chooseCctpFinality`.
Method: read the seams the way the 2026-09-13 pass read them — what does each side *assume* the other hands
over, and what happens on the tick after a refusal. Not covered here: the web's Solana library (read-only
observations at the end; the files were another session's that day), the yield service, the contracts.

Fix commit for every finding: **`35dc728`** (and `89e14dd` for observation O-8). Every regression test is in `agent/test/`. Severities follow the
2026-09-13 ledger: Medium = protection that could not fire or an action the design did not intend, within the
grant; Low = a consent boundary crossed without money moving.

Abbreviations: CCTP = Circle's Cross-Chain Transfer Protocol; HF = health factor; LP = liquidity provision;
PDA = program-derived address.

## Findings

### CC-1 · Medium · every bridge burn would have been refused as an unknown action (`agent/src/solana/baseBurner.ts`, 2026-09-25's own code)

**Where.** `KeeperBaseBurner.dispatch` translated the Solana record for the Base dispatcher — the Base account
in `account`, the burn hash in `txHash` — and left `action` as the Solana rung's name: `"derisk"` or
`"emergency-unwind"`. `KeeperDispatcher.dispatchBurn` (`keeperDispatcher.ts:697`) hands `record.action` to
`planBurn`, which keys its close fraction on it (`policy.ts:247`, `BURN_FRACTION`) and knows only
`"burn-derisk"` and `"burn-emergency"`.

**Failing scenario.** A linked pair, rung 3 fires on Solana, idle USDC short of the need, a Base burner
configured. The Solana dispatcher takes the bridge route → the adapter → `dispatchBurn` → `planBurn` returns
`REFUSE "unknown burn action derisk"` → the adapter returns REFUSED (not permanent) → the Solana dispatcher
returned REFUSED (see CC-2) → the monitor retried it to the attempt cap → abandoned, escalated. **No burn, no
sale, no repay: the rung was never acted on while the pair was linked.** The emergency rung is exempt from the
cap and would have refused every tick for ever.

**Why the tests did not catch it.** `base-burner.test.ts` faked `dispatchBurn` and asserted on the intent it
received; the fake never reached the planner. The Base side's own tests build Base records with the burn
action already on them.

**Fix.** `burnActionOf(solanaAction)` and a third argument to `toBaseRecord`; the adapter passes the action the
Solana dispatcher chose. **Regression.** `base-burner.test.ts` "KeeperBaseBurner over the real KeeperDispatcher
(mock chain)": the adapter drives the real `KeeperDispatcher` on `MockOilskin` — one `closeLpAndBurn` sent, the
message the mock router emits carrying `minFinalityThreshold` 1000 and `maxFee` = 2 bp of the expected 4,150 USDC
plus one unit, the receipt judged through the adapter on the Base account the bridge record carries; and "the
defect, pinned": the planner handed the untranslated record refuses by name, and a `burn-derisk` translation
leaves LP behind where an emergency closes everything.

### CC-2 · Medium · a rung refused "waiting for the burn in flight" was re-dispatched blind, and a Base refusal dead-ended the rung (`agent/src/solana/monitor.ts` resume path; `dispatcher.ts` step 3)

**Where, part 1.** `SolanaMonitor.resumePending` built its own dispatch intent — `{ record, persistBeforeSend }`
— while `evaluateOne` (the fire path) built the full one with `inFlightAgeS`, `onPairRead`, `onGrantRead` and,
since 2026-09-25, `persistBeforeBurn`. `RESUMABLE` includes non-permanent `REFUSED`.

**Failing scenario, part 1.** A burn is in flight (record A, bridge stage `burn-confirmed`, waiting on Circle).
The rung re-arms (A CONFIRMED but the HF did not move — the delivery is still to come) and fires record B; the
fire path hands the dispatcher `inFlightAgeS` = A's age → `bridgeDecision` says **wait** → B is REFUSED, not
permanent. **Next tick the resume path re-dispatches B with `inFlightAgeS` absent** → `null` → `bridgeDecision`
says **bridge** → a second `closeLpAndBurn`, a second amount across, while the first is still in Circle's hands.
The stall window (`AUDIT-2026-09-13` S-1) existed to prevent exactly this and was bypassed one tick after it
worked. Part 1 also meant a resumed bridge dispatch persisted no Base nonce and refreshed no pair record.

**Where, part 2.** `KeeperSolanaDispatcher.dispatch` returned the Base leg's REFUSED as the rung's result. A
Base refusal — no `closeLpAndBurn` grant, a half-link, unreadable LP state, a plan of NOTHING, or (after
`d0e4262`) Circle's Standard minimum above the fee ceiling — is not a state the Solana side can fix, and the
single-chain path (the reserve, then the keeper-funded sale, inside the Solana grant) is what the design says
stands in for the bridge. Instead the record retried the same refusal to the attempt cap. The fallback past the
stall window never triggered, because nothing was ever in flight.

**Fix.** One `dispatchIntent(record)` builder serves both paths. And a Base REFUSED falls through to step 4 the
same tick: the Solana plan runs inside the Solana grant, the Base refusal is carried on the result (`note` on
CONFIRMED, prefixed on a Solana REFUSED, logged at error when permanent). A Base **FAILED** is unchanged — it may
have gone out, and the persisted nonce and the receipt settle it before anything else acts.

**Regression.** `solana-monitor.test.ts` "AUDIT-2026-09-25 CC-2: a rung refused while a burn is in flight is
RESUMED with the in-flight age, the pair hook and the pre-burn write"; `solana-dispatch-bridge.test.ts` (new —
the dispatcher's bridge route with fakes for everything outside it): a REFUSED Base leg is answered by a Solana
sale the same tick with the reason on the note; both legs refusing names both in order and keeps the Solana
refusal's own permanence; a FAILED Base send is not answered on Solana; a burn in flight inside the window is a
wait and nothing else.

### CC-3 · Low · the bridge route ignored the owner's rung mask (`agent/src/solana/dispatcher.ts` step 3)

**Where.** The Solana grant carries `allowed_rungs`, the owner's per-rung consent, enforced on chain by
`keeper_protect` (`RungNotAllowed`) and off chain by `planProtect`. The Base grant (`Permission`) has no rung
mask. The bridge route ran before `planProtect` and never read the mask.

**Failing scenario.** An owner grants rungs 1–2 only ("warn me and repay from my reserve; never de-risk or
unwind"). Rung 3 fires on a linked pair with a Base burner: the Base leg closes two thirds of their LP and
burns it home — an action the owner excluded, taken on the other chain. Within the Base grant they signed, so
no money moves where they did not allow it; still a consent the product presents as per-rung, crossed.

**Fix.** The mask is checked before the Base leg is asked; a rung it excludes is REFUSED permanently, by name,
with the same words `planProtect` uses. **Regression.** `solana-dispatch-bridge.test.ts` "CC-3".

## Observations (no change; recorded so the next pass does not re-find them)

- **O-8 — closed the same day (`89e14dd`).** `KeeperSolanaDispatcher` cached the address lookup table and
  Circle's fee-recipient token account for the process lifetime, so a table extended after startup, or a fee
  recipient Circle changes, failed every delivery until a restart — the case the founder's first devnet run will
  produce, since a table is extended in chunks. A delivery whose simulation fails, or whose send does not confirm,
  now drops both caches and the next tick reads them afresh. Not a safety defect (the USDC waits in Circle's
  custody for any relayer); pinned in `bridge-stages.test.ts` "O-8".
- **O-9.** The allowance test in `chooseCctpFinality` runs on the *need*, which is the floor of what an emergency
  burn actually sends (everything). Documented in `baseBurner.ts`; the cost of being wrong is at most one Fast
  fee on a transfer Circle degrades anyway.
- **O-10.** A permanent Base refusal is logged and carried on the result but not escalated as
  `grant-misconfigured` unless the Solana path also refuses permanently. The owner learns from the record's
  note. Worth a notifier event when the two-key process exists.
