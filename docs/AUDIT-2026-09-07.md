### Addendum 2026-09-09 — M-HIGH-2's real fix: the venue-aware reader

**Keeper.** `agent/src/services/venues.ts` `VenueReader`: once per tick `router.REGISTRY()`, then per
collateral asset `venueOf`, `previousVenues`, `isEnabled`, then per distinct venue `PROVIDER()` (an
`AaveV3Venue` over the provider in `@zyo/shared` is the pool the G1–G4 valuation reads), `enabled()`
and `liquidationThresholdBps(asset)` for enabled assets; per account `healthFactor(account)`,
`debt(account, USDC)` and, on a non-Aave venue, `collateral(account, asset)`. `agent/src/engine/
venueValuation.ts`: four guards V1–V4 mirroring G1–G4 — the Aave venue must reproduce the pool
snapshot (V3); any other venue is accepted only when its health factor lies inside the band the
keeper's own Chainlink feeds imply from the venue's collateral, debt and threshold (min_i a_i/D ≤ HF
≤ Σa_i/D, a point for one collateral asset) within `ORACLE_DEVIATION_BPS` (V4); the combined verdict
is the WORST venue, UNKNOWN if any venue is UNKNOWN. `agent/src/services/accountValuer.ts` is the one
path `HealthMonitor` and `KeeperDispatcher.worldCheck` both value through. Startup: `VenueReader.
probe()` is fatal (`UnsupportedVenueError`) only for a venue that does not answer the interface; a
non-Aave venue that answers is the `NON-AAVE VENUE(S) IN THE REGISTRY` warning. Without a router the
keeper still values the Aave pool alone and says so (`VENUE READER OFF`).

**Web.** `readVenueHealth` → `AccountRead.venues`; `accountHf` is the worst venue's health factor and
`null` when the registry or any venue is unreadable or the Aave venue disagrees with the pool read
beyond the keeper's 1 % tolerance — the N-MED-2 behaviour (tile "unreadable", banner alert) is
unchanged; holdings and debt from a non-Aave venue appear on the dashboard with that venue's live
threshold. `readUnsupportedVenues` now means "does not answer `ICollateralVenue`" (`enabled()` false
or unreadable, threshold zero or unreadable for an enabled asset); a `PROVIDER()` view is no longer
required, so the Morpho venue is supported and the banner, the `venue-unsupported` grant state and
the wizard opt-out remain only for a venue the reader cannot talk to.

**What was NOT done.** `acceptVenue` was not introduced anywhere: `Deploy.s.sol` is untouched, the
registry's live pointer for cbBTC and WETH stays `AaveV3Venue`, no contract changed, and
`MorphoBlueVenue` is exercised only through mocks in these tests. Residuals are recorded in
`RISKS.md` §8: the router resolves the keeper's `unwind` to the first venue holding the asset, so an
account with positions on both venues for one asset may see the repay land on the healthier one
(then `confirm()` and the re-arm bound escalate); a cbBTC depeg beyond the bound makes a Morpho
position UNKNOWN rather than acted on early.

**Tests.** `agent/test/venueReader.test.ts` (23: Aave path unchanged with the venue cross-check; a

### M-INFO-2 — what was tried on the venue itself and did not break

* **Entry floor.** `borrow` executes Morpho's borrow (which enforces LLTV) and then checks the WORST
  market against `entryHfFloorWad`; `elapsed == 0` after the borrow so the debt read is exact.
  `openBorrowOnly`, `openLeveragedLp`, a raw `execBatch([permit2, supply, borrow])` and
  `createAccountAndExec` all pass through it (`MorphoEntryFloor.t.sol` M1–M5). No bypass found
  other than the documented raw-Morpho door (M8).
* **Worst-HF.** Minimum over markets; `type(uint256).max` when no market has debt; a market with
  `held == 0` and shares reads HF 0. Overflow bounds: `held × price` with the live 1e36-scaled
  prices is < 1e52 for any plausible balance — the same product Morpho computes.
* **Repay worst-first, spill, `max` by shares.** Insertion sort on HF, `owed == 0` skipped, whole
  markets repaid by shares, partial by assets; `repaid` decoded from every third result. The
  approval for a whole repay is `toAssetsUp(shares, expectedTotalBorrowAssets, totalBorrowShares)`;
  `MorphoMath.expectedBorrowTotals` mirrors morpho-blue `_accrueInterest` (third-order Taylor,
  virtual shares 1e6 / assets 1, fee shares dilute suppliers only) and `AdaptiveCurveIrm.borrowRate`
  and `borrowRateView` return the same `avgRate` for the same pre-accrual `market` struct, so the
  approval is exact to the wei against the real contract too. Not run against Morpho bytecode.
* **Live LLTV.** `_lltvBps = lltv / 1e14` from `idToMarketParams` on every call; a 77 % market says
  7700 (M7). Morpho LLTVs are multiples of 0.5 % so nothing truncates.
* **Empty-market disabled.** `enabled()` = `_collaterals.length != 0`; `_requireListed` also demands
  non-zero LT and LTV, so an enabled venue with no market for an asset is refused the same as Aave's
  cbZEC. One nit: the constructor accepts a Morpho *idle* market (`collateralToken == 0`,
  permitted by Morpho) and would list `address(0)` as a collateral; unreachable with the verified ids.
* **cbBTC market oracle = BTC/USD, no cbBTC leg.** Tried to turn this into an Oilskin-user loss and
  could not: for a borrower an oracle that ignores a cbBTC discount *delays* liquidation; the entry
  floor can be passed at a true HF below 1.55 during a depeg, but Morpho liquidates on the same
  oracle so the on-market risk is unchanged; the harm is lenders' bad debt (`RISKS.md` §8 records
  the assumption). Two things worth recording: Morpho's `ChainlinkOracle.price()` has **no
  staleness check**, so the venue's floor is only as fresh as the BTC/USD round; and after
  M-HIGH-2 is fixed the keeper's cbBTC/USD feed will disagree with the venue's HF by exactly the
  depeg — the keeper acting *earlier* is the right direction.
* **Callbacks / reentrancy.** `supplyCollateral` and `repay` are called with empty `data`, so
  Morpho makes no callback; `borrow` / `withdrawCollateral` have none. Every Morpho call is a plain
  `Call{callback: false}` from the account.
* **Real-ABI shape.** `position` (uint256, uint128, uint128), `market` (six uint128),
  `idToMarketParams` (five fields), `IIrm.borrowRateView(MarketParams, Market)`, `IOracle.price()`
  and `keccak256(abi.encode(params))` all match morpho-blue's public surface; the ids recompute
  on chain per the facts document.

## Scope 5 · `PythOracleAdapter` same-tx flag versus Foundry isolation

### P-MED-1 — the same-tx flag gates readers and liquidators the venue has no way to bundle (v1.1)

**Severity.** Medium for the v1.1 cbZEC market; Info today (the adapter is built, unused and not
deployed by default). Recorded now because Step 2 built the venue that would call it.

**file:line.** `contracts/src/oracle/PythOracleAdapter.sol:39` (`T_UPDATED` transient), `:90-104`
(`refresh` arms it), `:109-115` (`price()` reverts `NoUpdateInTx` unless armed **in this
transaction**), `:116` (then reads `getPriceNoOlderThan(PRICE_ID, maxAge)` anyway);
`contracts/src/venues/MorphoBlueVenue.sol:316-333` (`_marketHealth` calls `price()` for any market
where the account holds collateral — from `healthFactor`, `debt`, `borrow`, `repay`).

**Invariant broken.** "Views are plain reads" (`ICollateralVenue` doc comment) and Morpho's
liquidation liveness.

**Failing scenario (not executed; design).** A cbZEC/USDC market on this oracle is added to a
future venue (or the venue is rebuilt with its id).
(a) `eth_call venue.healthFactor(acct)` for any account holding cbZEC there → `NoUpdateInTx`. The
keeper (once venue-aware), the dashboard, and the router's `unwind` exit check
(`StrategyRouter.sol:286`) on *any* asset for that account all revert unless a `refresh` precedes
them in the same transaction; `MorphoBlueVenue` has no `refresh` hook and `unwind` cannot carry one.
(b) A generic Morpho liquidation bot calls `Morpho.liquidate` from its EOA → `_isHealthy` →
`price()` → revert. Only a liquidator who wraps `adapter.refresh{value}` + `liquidate` in one
contract call can liquidate, so the market Oilskin would own (`RISKS.md` §7) has a thinner
liquidator set and more bad-debt risk. (c) The flag is global for the transaction: once *anyone*
in the bundle refreshed, every `price()` call is armed — fine — but it adds nothing to safety:
`price()` re-reads `getPriceNoOlderThan(maxAge)` regardless, which already fails closed on a stale
feed. The flag only enforces "somebody paid to post an update in this transaction", i.e. it
punishes the case where the on-chain price is fresh because someone else just posted it.

**Recommended fix.** Drop the transient gate and keep the two checks that carry the safety
(max age against Pyth's own `publishTime`, and the TWAP peg breaker); keep `refresh` as the
permissionless way to make the price fresh. If a same-tx guarantee is wanted for Oilskin's *own*
flows, put it in the venue (a `refreshAndBorrow` / `refreshAndRepay` entry that bundles), not in
the oracle every third party must call.

**Regression test idea.** A test that reads `venue.healthFactor` as a separate top-level call
(`--isolate`, or `vm.prank` + a helper contract) on a market whose oracle is the adapter, and
asserts it answers; and a `MockMorpho.liquidate` path that succeeds from a plain caller.

### P-LOW-1 — the CI mode, measured; and no test of the production shape

**Measured on the founder's Mac (Foundry 1.8.1, `forge test --match-contract
PythOracleAdapterTest`):** default → **6 of 12 fail** (`NoUpdateInTx()` ×5, and
`test_poolUnreadableFailsClosed` fails with the *wrong* revert); `--isolate` → the same 6;
`--no-isolate` → 12/12. `forge test --isolate --no-match-contract "Invariant|BaseFork|
PythOracleAdapter"` → **262 passed, 0 failed** across 17 suites. So `--no-isolate` is needed by
exactly the six tests that call `refresh` and `price` as two top-level calls from the test contract
(`PythOracleAdapter.t.sol:119-131,133-145,147-154,162-181,183-191,193-199`), and by nothing else in
the tree — the account's transient lock, actor and peripheral slots are all set and cleared inside
one call. Commit `3c06c08`'s diagnosis is correct; its scope is narrower than "the suite".

**What is missing.** No test drives `refresh` and a Morpho read through *one* top-level call —
the only shape a production bundle can have (an EOA cannot make two calls in one transaction;
`acct.execBatch([{adapter, refresh, value}, {venue, borrow}])` or a bundler contract can). The
six tests prove the flag works inside a Foundry test frame, which is not a transaction shape any
user or liquidator has. `contracts/foundry.toml` does not set `isolate`, so a fresh clone's plain
`forge test` is red and `README.md:100` still advertises the old command and count.

**Recommended fix.** Rewrite the six tests to call a tiny `PythBundle` helper (one external
function: `refresh` then `price`, or the account's `execBatch`) so they pass under `--isolate`,
then run CI in the default mode; add `isolate = true` to `foundry.toml` explicitly and delete the
flag from `ci.yml`; fix `README.md:100`. If the founder prefers to keep `--no-isolate`, pin it in
`foundry.toml` (`isolate = false`) so local and CI agree without a flag, and add the bundle test
anyway — it is the production shape.

**Regression test idea.** `test_refreshAndPriceThroughOneTopLevelCall` green under both modes; a
CI matrix leg with `--isolate`.
